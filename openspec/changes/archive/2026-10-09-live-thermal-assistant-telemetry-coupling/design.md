## Context

- `crates/flight_core` implements `CirclingStateDetector` (`circling.rs`), `WindEstimator` (`wind.rs`) and `ThermalCoreCalculator` (`thermal.rs`). They are composed only inside `BoundedFlightPipeline::step`, which is exercised by Rust tests/benchmarks. Two deviations from the existing `dynamic-thermal-assistant-wind-drift` spec exist there: the core buffer is not reset on `CIRCLING → GLIDING`, and the thermal snapshot is only produced once a barometer sample has arrived.
- No Rust code is linked into the app. The airspace feature already follows a "Rust reference + Dart runtime" pattern (Kotlin plugin does not implement the airspace channel; Dart fallback in `brandyfly_native_method_channel.dart` runs).
- UI telemetry path: `ITelemetrySource.telemetryStream` → `TelemetryRepository.onSnapshot` → `ValueNotifier<CockpitTelemetry>` → `widget_slot.dart` selectors. Replay path: `FlightReplayService.currentTelemetry` (untyped map) → `CockpitTelemetry.fromMap`. Replay can advance by >1 point per tick (speed multiplier) and `seekTo` jumps arbitrarily.
- Fabricated wind (`heading + 180`, `12 km/h`) is injected in `SyntheticTelemetrySource`, `TelemetrySnapshot.fromFlightPoint`/`toTelemetryMap`, `FlightReplayService.currentTelemetry`, and `TelemetryRepository.onSnapshot`; `CockpitTelemetry` has non-null wind defaults (`220°`, `14 km/h`).
- `ScreenAutoSwitchTrigger.{onThermalCircling,onGlideStraight}` exist in config and settings UI; nothing acts on them. `ScreenManagerService.setActiveScreen` does not distinguish manual vs automatic.

## Goals / Non-Goals

**Goals:**
- One deterministic thermal-assistant state machine, specified once in Rust and ported 1:1 to Dart, with machine-checked parity.
- A single place (`TelemetryRepository`) where live and replay telemetry are turned into thermal-assistant state, so every widget sees the same values.
- Explicit absence: nullable/validity-tagged wind and core everywhere instead of defaults.

**Non-Goals:**
- Background isolate for the engine (see Decision 3).
- Changing the circling/wind/core thresholds or algorithms beyond the gap/stale/reset rules required by the new spec.

## Decisions

### 1. Add a `ThermalAssistant` orchestrator in Rust and port it to Dart
Create `crates/flight_core/src/thermal_assistant.rs` composing the three existing components with the new rules: skip stale/invalid samples, treat a > 5 s gap as interruption (reset circling detector + wind turn accumulation, keep last wind estimate), reset core buffer and track window on `CIRCLING → GLIDING`, compute output on every GPS sample (no baro dependency). `BoundedFlightPipeline` delegates to it, fixing both existing deviations.

Port to `apps/mobile/lib/domain/thermal_assistant/` as pure Dart (no Flutter imports): `heading_tracker.dart`, `circling_detector.dart`, `wind_estimator.dart`, `thermal_core_calculator.dart`, `thermal_assistant_engine.dart`, `thermal_assistant_state.dart`. Mirror Rust structure and arithmetic order (f64 throughout, same equirectangular projection constants) so parity tolerances can be tight.

- *Alternative: package Rust via FFI (cargokit/native assets).* Rejected for this change (user decision): large build/CI/ABI scope, needs a Web fallback anyway, and needs real-device gates. The orchestrator boundary chosen here is exactly the API a future FFI change would expose, so that migration stays a drop-in replacement.
- *Alternative: port only to Dart and drop Rust.* Rejected: Rust is the documented owner of deterministic flight calculations and the replay/benchmark harness.

### 2. Golden fixtures generated by Rust, checked in, verified both sides
New bin `crates/flight_core/src/bin/thermal_fixtures.rs` builds scenarios deterministically (no-wind thermal, 10 m/s drift thermal, straight glide, erratic reversals, 8 s telemetry gap, stale-flagged samples) and writes `packages/contracts/fixtures/thermal_assistant/<scenario>.json` with `{ schemaVersion, inputs: [{tMs, lat, lon, headingDeg, climbMs, stale}], expected: [{mode, turn, wind?: {speedKmh, dirDeg, valid}, core?: {lat, lon}}] }`. JSON is formatted by hand (fixed precision) to avoid adding serde to a dependency-free crate.
- A Rust test regenerates fixtures in memory and asserts byte equality with the checked-in files (catches stale fixtures in `cargo test`).
- A Dart test (`test/domain/thermal_assistant_parity_test.dart`) loads the fixtures from the repo path and asserts per-sample parity within spec tolerances.

### 3. Run the engine synchronously in `TelemetryRepository` on the UI isolate
At 10 Hz the per-sample work is O(window) over ≤ 600 core points (60 s) — sub-millisecond in Dart AOT. The audio vario is fed independently (native synthesizer driven by `AudioVarioService`), and sensor acquisition is native, so neither hot path waits on this work.
- *Alternative: dedicated isolate.* Rejected: message-passing and copying the track window each tick costs more than the computation, adds lifecycle complexity, and makes replay determinism harder to test. Revisit only if the benchmark task shows > 1 ms mean.
- Battery: negligible additional CPU; no extra wakeups (driven by existing telemetry ticks).

### 4. Typed state on `CockpitTelemetry`; nullable wind
Add `ThermalAssistantState thermal` (defaults to an idle state) to `CockpitTelemetry` containing `FlightMode mode`, `TurnDirection turn`, `WindEstimate? wind` (`dirDeg`, `speedKmh`, `updatedAt`, `isStale` derived at 15 min), `CoreOffset? core` (meters east/north relative to pilot), and an unmodifiable circling track window (`List<ThermalTrackSample>` with east/north meters relative to the pilot, climb, timestamp). Make `windDir`/`windSpeed` nullable (derived from `thermal.wind`). Remove fabricated wind from all four injection sites; `TelemetrySnapshot.windDirectionDeg/windSpeedKmh` stay as optional pass-through for future real wind sources only.
- Track window keeps at most one sample per second (~20 bubbles per turn; denser trails rendered as an unreadable band on device) and is rebuilt as a new list only when a sample is appended. Widget selectors key on a monotonically increasing `thermal.revision` to keep rebuild budgets intact (`test/perf/rebuild_budget_test.dart`). `CockpitTelemetry.hasSource` distinguishes live/replay data from idle preview telemetry.

### 5. Replay: feed every point, restore checkpoints on seek
A `ReplayThermalTracker` (data layer) owns a replay-only engine and tracks the last fed point index. On each replay notification it feeds points `(lastFed, currentIndex]` in order (handles speed multipliers and forward seeks), and stores a deep copy of the engine as a checkpoint every 60 s of flight time. On a backward seek it restores the latest checkpoint at or before the target and feeds forward (≤ 60 s of points), so the state is exactly that of a continuous replay. The replay slider fires a seek per drag event, which is why per-seek cost must be bounded.
- *Alternative: rebuild from up to 120 s before the target.* Rejected: wind estimated earlier in the flight would be lost, so the state would differ from a continuous replay.
- *Alternative: rebuild from flight start on each seek.* Rejected: O(flight length) per drag event (~100 ms+ for long flights) makes scrubbing janky.
- Memory: checkpoints copy only references to immutable samples (≤ 300 s track window, ≤ 60 s core window); ~2 MB for a 3 h flight. Restored engines bump their revision past any previously published value so UI selectors always rebuild.
`FlightReplayService.currentTelemetry` stops emitting wind; replay `CockpitTelemetry` gets `thermal` from the tracker.

### 6. Auto-switch as a separate controller
New `ScreenAutoSwitchController` (service layer) listens to `TelemetryRepository.telemetry`, reacts only to `mode` transitions, and calls `ScreenManagerService.setActiveScreen(id, automatic: true)`. `setActiveScreen` gains a named `automatic` flag; manual calls (default) record the override time for the 60 s suppression. Rules from the modified `screen-widget-configuration` spec: 10 s minimum spacing, suppressed in edit mode, remember pre-switch screen, prefer first `onGlideStraight` screen on exit. Clock is injectable for tests.
- *Alternative: put logic inside `ScreenManagerService`.* Rejected: it would make the config service depend on telemetry and complicate its existing tests.

### 7. Synthetic wind
`SyntheticTelemetrySource` gains `windFromDeg`/`windSpeedKmh` (default 0). Ground velocity = air velocity (from heading/airspeed) + wind velocity; reported `heading` remains the air heading, `speed` becomes ground speed. The simulation overlay gets a simple wind speed/direction control so mock flights exercise estimation.

### 8. Thermal map widget input
`ThermalMapWidget` receives `List<ThermalPoint>? trackPoints` (already supported), `Offset? coreOffset`, `double headingDeg` (track heading), nullable wind, and `bool preview`. `_resolveTrackPoints()` returns the demo spiral only when `preview == true`. `widget_slot.dart` passes `t.heading`, not `t.windDir`.

## Risks / Trade-offs

- [Dart and Rust implementations drift over time] → Checked-in golden fixtures verified in both `cargo test` and `flutter test`; fixture regeneration is a single command documented in `docs/development.md`.
- [Floating-point differences between Dart and Rust] → Both use IEEE-754 f64 with identical operation order; tolerances (0.5 km/h, 2°, 2 m) leave margin. Mode transitions must match exactly; fixtures avoid samples sitting exactly on thresholds.
- [Removing fake wind leaves wind widgets empty on many flights] → Intended (honest data); "no estimate" UI is explicit and wind appears after two turns. Documented in release notes.
- [Engine on UI isolate causes jank] → Benchmark task with 1 h @ 10 Hz; bounded windows; fallback to isolate is a contained change behind the repository.
- [Auto-switch surprises pilots] → Only screens explicitly configured with a trigger switch; manual override cooldown; rate limit; no switch during edit mode.
- [Phone GPS heading noise at low speed causes false circling] → Existing 270°/25 s threshold plus stale/invalid filtering; real-device validation listed as a release gate rather than claimed here.

## Migration Plan

- No persisted data changes: `ScreenAutoSwitchTrigger` values already exist in saved configs; wind/thermal state is in-memory only.
- Rollback: revert the change; no data migration required.
- Release gate: real-device thermal flights (Android + iOS) to validate circling detection with phone GPS heading noise before advertising the thermal assistant as flight-ready.
